I found four P1s in Phase 8.2. The most consequential are a subject-detail response that can change when a hidden policy triggers a failed authorization check, and a DirectResponse that can appear in a Gateway relation despite D-129. This was a read-only review. I used the author’s test results and did not run the suites.

## P1

1. **P1 · architecture — A hidden policy can turn a readable subject detail into a 503.** The relation handler batches SARs for raw candidates before applying the downstream authorizer. Consider a policy that the downstream authorizer denies, in a namespace and kind bucket the request would otherwise never query. When that policy names the subject, its bucket enters the batch. A SAR error for that bucket now replaces the entire detail response with `503 authz-unavailable`. With the policy absent, the request can return 200. This breaks design §7.5 and D-085 below the request cap, so D-112’s size-limit exception does not cover it. The relation path needs to eliminate candidates already denied by the downstream authorizer before issuing their SARs. [relations.go](../../../../pkg/api/relations.go:38) · [visible.go](../../../../pkg/api/visible.go:112) · [commit.go](../../../../pkg/api/commit.go:183)

2. **P1 · correctness — DirectResponse status produces subject relations.** `installPolicies` includes list-only policies and the relation handler passes their ancestors to `policy.Relations`. The checked-in kgateway 2.3 DirectResponse fixture already has a current `Attached=True` Gateway ancestor, so it can appear under **Reported attached here**. D-129 and design §6.6 reserve those ancestors for policy findings. The new relation path must honor the list-only classification. 3. **P1 · correctness — A policy relation can advertise a detail link that returns 404.** A D-119 authorizer can allow a policy as a population member and deny its named read, as the existing `denyNamed` test double demonstrates. The relation and list row build the link with population authorization. The destination requires named authorization. The policy may remain visible as a member under design §7.1, but the detail link must honor the named decision. The list UI also supplies a destination unconditionally, so suppressing the API link alone would leave the broken navigation in place. The axe click times out, and the separate Playwright round-trip test skips when it finds no linked target. The reported live-cluster run does not establish the brief’s matrix acceptance criterion. ## P2

5. **P2 · correctness — D-135 leaves freshness dependent on the generation of `Attached`.** `PolicyFreshness` skips optional types only in the `Pending` reason loop. The preceding stale check still includes `Attached`. A current `Accepted=False/Invalid` beside an older `Attached=False/Pending` therefore suppresses KGWUI-002, emits KGWUI-003, and omits the rejection from the policy summary. The added tests move both conditions to the old generation together. D-135 says `Accepted` decides the ancestor’s freshness. An older `Attached` should be kept out of positive attachment evidence independently. [own.go](../../../../pkg/health/own/own.go:364) · [checks_test.go](../../../../pkg/health/checks_test.go:438) · [D-135](../../../../docs/decisions.md:1844)

6. **P2 · architecture — The ancestor finding and relation paths use different visibility rules.** Policy currentness requires list and named access, plus access to the Gateway behind a ListenerSet ancestor. The KGWUI-002 basis records only the ListenerSet, and the generic finding projector accepts population **or** named access. A viewer can therefore see an ancestor marked `unreadable` on the policy page and receive the finding that judged the same ancestor current. D-134 permits membership changes as install context and explicitly retains the ListenerSet parent readability rule. Sharing `PolicyFreshness` addresses the status guard. The finding projection also needs the policy ancestor’s visibility requirements. [policies.go](../../../../pkg/api/policies.go:127) · [status.go](../../../../pkg/health/own/status.go:150) · [rollup.go](../../../../pkg/health/rollup.go:56) · [D-134](../../../../docs/decisions.md:1837)

7. **P2 · architecture — The E7 relation contract loses registered ListenerSet kinds.** The API candidate pass recognizes every served `CategoryListenerSet`, while `pkg/policy` recognizes only the two upstream group/kind pairs. A downstream ListenerSet with the documented shape gets a detail page and its Gateway’s policies reach the candidate set, but the shared join drops its own parent relation and the route’s second hop through it. A kgwctl caller with the correct one-shot catalog and lookup cannot supply the missing classification. Use the same caller-supplied classification and declared-hop logic for candidate selection and relation construction. [relations.go](../../../../pkg/api/relations.go:117) · [E7 parent join](../../../../pkg/policy/relations.go:108) · [ListenerSet recognition](../../../../pkg/policy/relations.go:163) · [kinds.go](../../../../pkg/kinds/kinds.go:4)

8. **P2 · architecture — D-136 changes the meaning of a v1 link while leaving its destination implicit.** The implementation replaces existing `yaml` links while D-136 remains proposed and the plan requires additive v1 changes. A pre-8.2 shell routes the new policy `detail` links to ListenerSet pages. The new shell can make the same mistake for kgateway policies if `/meta` is late or unavailable, because the generic link resolver falls through to `listenersets` until a module-global registry is populated. Findings and diagnostics use that resolver. Resolve the compatibility decision explicitly and make the destination dependable wherever a policy link appears.

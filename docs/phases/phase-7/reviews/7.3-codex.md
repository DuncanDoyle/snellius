1. **P1 — In-flight requests can commit using a stale or replaced session identity.** [middleware.go:66](../../../../pkg/auth/session/middleware.go:66), [middleware.go:84](../../../../pkg/auth/session/middleware.go:84)

   The commit check compares only the session’s `AuditID`. It accepts an identity past `freshUntil` whenever refresh is possible. A successful refresh also replaces `sess.info.Identity` without changing that ID ([refresh.go:112](../../../../pkg/auth/session/refresh.go:112)), while the request retains its original identity.

   A request can therefore start with privileged groups, block while refresh removes those groups, and commit data authorised with the old groups. Crossing token expiry while refresh is pending also passes this check. Rebuilding for SAR expiry retains the same old request identity. This violates §4.4’s prohibition on serving a stale identity; fresh SARs cannot correct stale groups supplied to them.

2. **P1 — Gateway prefetch lets a hidden route change a visible response into 503.** [lists.go:263](../../../../pkg/api/lists.go:263)

   `prefetchGatewayRows` batches each not-accepted route together with **all its parents**, before determining whether the route is readable. The rendering path correctly short-circuits on the route’s denial at line 281.

   Reproducer: a readable Gateway has a not-accepted route in a denied namespace. Add another parent to that hidden route in namespace `fresh`; make the Gateway SAR for `fresh` fail. Prefetch now records the unnecessary error and the wrapper returns 503, whereas serial rendering never asks that question and returns 200. Enough such parents can similarly exhaust the check cap. Hidden-object changes thus affect the viewer’s response, contrary to D-085 and Task 26’s pruning requirement. Resolve route visibility before collecting its parents.

3. **P2 — Full-read evaluation detaches cancellation before admission.** [fullread.go:126](../../../../pkg/auth/sar/fullread.go:126)

   `evaluate` applies `context.WithoutCancel` before its constituent checks reach the limiter. Consequently, cancelling a full-read leader while its SARs are queued neither releases those queue positions promptly nor prevents their eventual submission. Workers can continue scheduling additional kinds after cancellation.

   Task 26 explicitly requires queued checks—including full-read constituents—to use the leader’s request context, detaching only after admission. Under load, abandoned requests consume queue capacity and SAR budget until the evaluation timeout, causing avoidable failures for active viewers. Existing queued-cancellation tests exercise `AuthorizeErr`, leaving this path uncovered.

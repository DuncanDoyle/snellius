# Review: 7.2 TokenReview audience fix (D-097)
Reviewer: Codex (cross-model). Range: 472f098..58f743f.


No P1 correctness/security bug found. The fix preserves client binding on both login and refresh, with two documentation mismatches and one test gap.

1. **P2 — D-097 overstates the cluster requirement.** [docs/decisions.md:1479](/Users/ddoyle/Development/claude/snellius-phase7/docs/decisions.md:1479) says the API server **must accept Snellius’s client ID**. Counterexample: a signed token has `aud=["snellius","cluster"]`, `azp="snellius"`, and the cluster accepts only `"cluster"`. Local validation passes; TokenReview also passes because Kubernetes requires any configured audience to match. This preserves the signed binding to Snellius, but contradicts the stated requirement. Describe acceptance of the token through an overlapping audience instead. [Upstream audience validation](https://github.com/kubernetes/kubernetes/blob/v1.35.0/staging/src/k8s.io/apiserver/plugin/pkg/authenticator/token/oidc/oidc.go#L767-L807).

2. **P2 — Acceptance documents still require the removed `audience` reason.** [phase-7.2-brief.md:17](/Users/ddoyle/Development/claude/snellius-phase7/docs/phases/phase-7/phase-7.2-brief.md:17) requires `/signin-failed?reason=audience`; [implementation-plan.md:201](/Users/ddoyle/Development/claude/snellius-phase7/docs/phases/phase-7/implementation-plan.md:201) still lists it. These conflict with D-097 and the implementation. No executable producer or consumer of `ReasonAudience`, `ErrAudience`, or the literal failure reason remains; the residual dependency is documentary.

3. **P3 — Tests do not cover the newly decisive audience combination.** [tokenreview_test.go:54](/Users/ddoyle/Development/claude/snellius-phase7/pkg/auth/oidc/tokenreview_test.go:54) tests success with absent response audiences, while [refresh_test.go:41](/Users/ddoyle/Development/claude/snellius-phase7/pkg/auth/oidc/refresh_test.go:41) covers only a wrong single audience. Add login/refresh cases where TokenReview succeeds with API audiences unrelated to the client: reject local wrong `aud`, missing/wrong multi-audience `azp`; accept matching `aud`/`azp`; verify the exact token was reviewed. This would lock down the security invariant replacing the removed checks.

The security reasoning is sound:

- [login.go:332](/Users/ddoyle/Development/claude/snellius-phase7/pkg/auth/oidc/login.go:332) requires the client in `aud`, requires `azp` for multiple audiences, and rejects any present mismatching `azp`. Login and refresh both apply this to the same raw token subsequently reviewed.
- Multiple JWT authenticators do not let another issuer satisfy local `iss` validation. Kubernetes also checks issuer and verifies the token before returning identity. Accepting the token through another **shared audience** does not remove its signed Snellius audience. [Upstream authenticator](https://github.com/kubernetes/kubernetes/blob/v1.35.0/staging/src/k8s.io/apiserver/plugin/pkg/authenticator/token/oidc/oidc.go#L796-L807).
- Omitted review audiences default to API audiences; returned audiences therefore are not proof of the JWT’s client audience. [TokenReview implementation](https://github.com/kubernetes/kubernetes/blob/v1.35.0/pkg/registry/authentication/tokenreview/storage.go#L89-L116).

This conclusion assumes the trusted cluster authenticates the token correctly; TokenReview does not identify which authenticator accepted it.

No files edited. Tests were not rerun; the supplied author results were considered.

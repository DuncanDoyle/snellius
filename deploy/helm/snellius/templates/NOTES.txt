Snellius is installed. It is read-only.
{{- if eq (include "snellius.authMode" .) "local" }}
Snellius runs in local mode: it listens on the Pod's loopback only.
Anyone who can port-forward to it sees everything it reads (never Secrets),
which can be more than their own Kubernetes RBAC allows.

Open it with:
  kubectl -n {{ .Release.Namespace }} port-forward svc/{{ include "snellius.fullname" . }} 8080:80
then browse to http://localhost:8080
{{- else }}
Snellius runs in secure mode.
{{- $redirect := include "snellius.oidcValue" (dict "root" . "key" "redirectURL") }}
{{- $u := urlParse $redirect }}

At the identity provider, register:
  Redirect URL:             {{ $redirect }}
  Post-logout redirect URI: {{ $u.scheme }}://{{ $u.host }}/

The Kubernetes API server must accept tokens for client ID "{{ include "snellius.oidcValue" (dict "root" . "key" "clientID") }}".
Either use the same client ID as the cluster, or add it as an extra audience
in the API server's structured authentication configuration.
Check that the cluster accepts your token with:
  kubectl auth whoami

Allowed permission checks are reused for {{ include "snellius.authzValue" (dict "root" . "key" "cacheTTL") | default "60s" }} (auth.authz.cacheTTL).
That is how long a revoked permission can stay visible in Snellius;
a longer TTL trades that freshness for fewer checks on the API server.
Denied checks are reused for 5m, so a new grant shows within 5 minutes.

It is exposed through an HTTPRoute.
{{- end }}
{{- end }}

Controller metrics are read directly from the controller pods on port 9092.
If a NetworkPolicy blocks that, the UI reports "signal unavailable" instead of green.
